# 02 · picked fields: results, 2026-11-07

**Verdict: the pick works, the check is not met, the stop is not hit. The experiment stays open.**
When the model chose the fields, it chose exactly the needed ones every time (60 of 60), and the two-call path used
24% of the whole file's input tokens. But `picked` answered 58 of 60 against `toml`'s 60 of 60: 3.3 points behind,
and the check allows 2 (one answer, at n = 60). The hand-fed `view` control scored the same 58 of 60, so the gap
does not come from the pick.

Data: `repos.toml` (82 repos, 16 fields, sha256 prefix `99ccf2db`). 20 generated questions, 3 passes, Haiku 5.5
(`claude-haiku-5-5`) through `claude -p` with no tools, 240 calls, 0 errors. Script: `bench.py` in this folder,
imports 01's questions, views and scoring. Token counts are Claude's own, from the usage report. Run table:
`20261107T143111Z-haiku.md`. A one-pass smoke run of `picked` (20 of 20, $0.02) came first, to check the parser;
its numbers are not used.

## What it shows
- **The pick was not the weak point.** All 60 picks covered every needed field, none added a field, none was
  malformed, none named a column that doesn't exist. The cost of choosing is one call: +1,171 tokens, or +48% over
  the hand-fed `view`.
- **Against the prediction (README):** coverage 100% (predicted 95% or more). Total 3,602 tokens, 24% of `toml`
  (predicted 3,100, 22%): call 1 was 120 over, call 2 was 400 over. The in-run `view` control is also 2,432, so
  the data got bigger since 01 (2,028); why is UNKNOWN.
- **Accuracy: the four misses were all call 2 reading a correct view.** q06 (a count, off by 1 in `picked` and by 3
  in `view`), q15 (one repo too many in `view`) and q17 (six repos too many in `picked`; the `remote` view leaves a
  default remote empty, which is the likely cause, not checked). Both `picked` misses had a correct pick. `toml` happened to
  score 60 of 60 here, against 58 of 60 in 01: two answers either way is inside the noise of 20 questions.
- **The second call costs more time than the file does.** A `picked` question took 9.2 s on average (median
  8.95), `toml` 5.7 s (5.15). Four jobs ran in parallel, so these are rough, but two sequential round trips
  to Haiku took longer than one call that reads 14,861 tokens.
- **Per token it is still ahead:** 0.268 correct per 1k tokens, 4.0× the file as it is, against 5.9× for the
  hand-fed view.

## Limits
- The questions name their fields ("status", "platform", "remote"), so picking was the easy case. A vague
  question is the real test of the pick, and this run does not make it.
- The two calls are separate `claude -p` processes and each pays about 870 tokens of fixed overhead. In one live
  conversation the second step would not, which would put `picked` near 2,730 tokens, 18% of `toml` (inferred
  by subtracting 872, not measured).
- One file, 20 mechanical questions, n = 60 per view. The README's check allows a one-answer gap; this run was
  two behind.
- The cost estimate in the README was $0.30; the run's reported `total_cost_usd` is $0.14 at list prices, and it
  ran on the subscription.
